## 四、问题与解决
**遇到的问题**
1. Hive容器编排启动顺序问题，metastore反复连不上MySQL；
2. 一开始打算直接使用UPDATE更新Hive普通表字段，发现语法不可用；
3. CSV导入后实际行数和预期不一致，多出一行；
4. 缺失值处理方案选择，不确定填充还是直接丢弃。

**AI是否有有效解决参考**
1. 有效：AI提示增加MySQL健康检查，metastore等待数据库就绪；
2. 有效：AI提醒Hive普通表不支持UPDATE，推荐CTAS新建表方式；
3. 有效：AI提示检查skip.header.line.count表头跳过参数；
4. 部分有效：AI给出多套方案，最终方案需要自己结合业务确定。

**最终如何解决**
1. 在compose配置中增加healthcheck健康检测，调整服务依赖顺序，三个容器正常启动；
2. 全部清洗逻辑改用CTAS方式生成DWD清洗表，放弃UPDATE写法；
3. 修正表头跳过参数，重建表重新导入，行数校验符合预期；
4. 自主确定清洗规则：年龄用均值填充，异常邮箱标记unknown，上架日期按同品类规则补齐，不直接丢弃数据。

## 五、反思与总结
**AI协同带来的价值**
AI可以提供语法模板、报错排查方向、SQL思路参考，省去翻阅大量文档找语法的时间；环境编排、Hive常见坑点可以快速给到参考，提升调试效率。整个任务的核心拆解、逻辑设计、上机验证、问题定位都由自己完成。

**本次协作中我的能力提升**
熟练掌握docker-compose多服务编排、healthcheck健康依赖配置；独立完成Hive ODS建表、数据导入、五维度质检、开窗去重、缺失值清洗全套SQL开发；养成规范的开发习惯：上机跑通、核对行数、留存日志、记录坑点；建立明确意识：AI给的所有参考内容，都必须人工核验、测试后才能使用。

**AI协同的局限与风险（准确性/合规性/依赖）**
1. 准确性：AI看不到我们专属的数据字典，字段名、字段类型经常推断出错，如果直接复制会导致建表失败，必须人工逐条核对；
2. 合规性：本次模拟教学数据，开发时依然配置.gitignore，做好数据和密钥隔离，防止真实业务数据误提交入库；
3. 依赖风险：不能直接无脑复制AI代码，开窗函数、COALESCE、CTAS这些核心逻辑，自己要吃透原理；答辩如果被追问实现逻辑，必须独立讲清楚。

**对AI协同的改进建议**
1. 后续先把项目说明文档、完整数据字典提前给到AI，减少AI自行推断字段带来的错误；
2. 让AI只输出验证步骤、检查清单，代码由自己独立编写，边写边验证；
3. 团队统一提示词规范，大家参考AI的标准一致，减少版本差异。
