# 架构设计文档（最终版）

**项目**：云购生活新零售企业——企业级数据仓库与经营分析可视化系统
**团队**：200A　|　**成员**：陈劲松、王志达、刘畅、刘正扬
**版本**：v2.0（第 5 周 · 整合第 1~4 周全部架构落地）
**文档日期**：2026-11-23

## 一、设计目标与原则

1. **分层解耦**：贴源、清洗、明细、汇总、应用各层职责单一，上游变更只影响相邻层；
2. **可追溯**：清洗过程分层留痕（stg1 → stg2 → stg3），任何一刀切处理都能回溯到中间层；
3. **可复用**：DWD 明细层一次建模，DWS/ADS 与可视化均从同一明细底座取数；
4. **口径唯一**：所有指标统一从 DWD 计算，ADS 只做聚合不另起炉灶；
5. **可复现**：全链路一键重建脚本 + Docker Compose 编排，环境即代码；
6. **性能可控**：事实表按日期分区、ORC 列式存储，配合分区裁剪控制扫描量。

## 二、总体架构

系统自下而上分为五大部分：数据源与存储层、数仓计算层（四层 + STG 清洗管道）、分析建模层、AI 交互层、可视化与部署层。

【插入图片：dw_architecture.png】

**数据流向**：

```
业务 CSV（6 张源表）
  → ODS 贴源层（TEXTFILE，原样不动）
  → STG 清洗管道（三站串联，DROP PURGE + CTAS）
  → DWD 明细层（星型模型，ORC，366 动态分区）
  → DWS 汇总层（五粒度日汇总宽表）
  → ADS 应用层（六张主题集市表）
  → ├→ KPI 结果表 / 预测建模（Python）
  ├→ Superset 仪表板（经 MySQL 报表镜像库）
  ├→ ECharts 数据大屏（JSON 静态装配）
  └→ Streamlit NL2SQL 问答（Hive beeline / MySQL 双后端）
```

## 五、DWD 星型模型设计

以订单分析场景为核心选择**星型模型**：订单事实表居中，四张维度表环绕，明细事实表独立成表。

| 表 | 类型 | 粒度 | 关键字段 | 分区/存储 |
| --- | --- | --- | --- | --- |
| dwd_order | 事实表 | 一笔订单一行 | order_id、user_id、store_id、pay_amount、discount_amount、pay_type、order_status、channel、order_timestamp | 按 order_dt 动态分区 366 个，ORC |
| dwd_order_item | 明细事实表 | 一行一个明细项 | item_id、order_id、product_id、quantity、unit_price、item_amount | ORC，异常单价由商品维表回填 |
| dim_user | 维度表 | 一位用户一行 | user_id、gender、age、region、member_level、phone、email | 全量 1,000 行 |
| dim_product | 维度表 | 一款商品一行 | product_id、product_name、category、brand、price、cost | 价格异常已按品类中位价修正 |
| dim_store | 维度表 | 一家门店一行 | store_id、store_name、province、city、region | 覆盖 15 省份直辖市 |
| dim_date | 维度表 | 一天一行 | date_id、year、month、day、week、is_weekend | 2024 全年 366 行（闰年） |

**分区策略**：事实表按订单日期 `order_dt` 一级分区，`INSERT OVERWRITE ... PARTITION(order_dt)` 动态分区装载，显式设置 `hive.exec.max.dynamic.partitions=1000`（默认上限 100，366 分区必然超限，已实测踩坑）。分区裁剪经 `EXPLAIN` 验证生效（带谓词查询 4.90s vs 全表 5.37s）。

**DWS 汇总设计**：五张汇总表覆盖"天×整体、天×品类、天×门店、天×渠道、用户全期"五个粒度，全部从 DWD 聚合生成，为 ADS 提供统一宽表来源。

**ADS 应用设计**：六张主题表一一对应看板主题——KPI 大盘（ads_kpi_overview）、GMV 趋势（ads_gmv_daily）、品类排行（ads_category_sales）、门店排行（ads_store_sales）、渠道分布（ads_channel_sales）、用户价值分层（ads_user_value）。

## 六、技术选型

| 类别 | 选型 | 选型理由 |
| --- | --- | --- |
| 数仓计算 | Apache Hive 4.0.0 | 企业级 SQL on Hadoop 事实标准，支持动态分区/窗口函数/ORC，教学与生产一致 |
| 元数据 | MySQL 8.0 | Hive Metastore 后端存储，成熟稳定 |
| 分析引擎 | Hive on beeline / MySQL pymysql | 双执行后端：数仓侧走 Hive，报表镜像侧走 MySQL，按 NL2SQL_BACKEND 切换 |
| 报表镜像 | MySQL 8.0（12 表镜像） | BI 工具直连 Hive 较重，将 ADS/DWS 镜像到 MySQL 供 Superset 低延迟取数 |
| BI 仪表板 | Apache Superset 6.1 | 开源、图表丰富、支持 REST API 自动化配置 |
| 数据大屏 | ECharts 5.5（单文件离线） | 无外网依赖、1920×1080 scale 自适应、地图合规（阿里 DataV GeoJSON） |
| 问答应用 | Streamlit + Plotly | 轻量 Web 闭环：提问 → NL2SQL → 结果 → 自动图表 |
| NL2SQL | 规则引擎 + LangChain 双链路 | 无 LLM Key 时规则兜底可用，有 Key 时语义增强 |
| 预测建模 | Python（statsmodels/三模型对比） | 移动平均/线性回归/霍尔特线性趋势 + 2 基线，MAE/MAPE 量化评估 |
| 容器化 | Docker Compose（6 服务） | 一键编排 mysql/hive-metastore/hive-server/clickhouse/superset/app，healthcheck 全链路 |

## 七、部署架构

Docker Compose 六服务编排，全链路 healthcheck + depends_on 保证启动顺序：

| 服务 | 端口 | 职责 |
| --- | --- | --- |
| mysql | 3306 | Hive Metastore 元数据 + 报表镜像库 |
| hive-metastore | 9083 | 元数据服务（TCP 探活） |
| hive-server | 10000 | HiveServer2（beeline 接入，NL2SQL 后端之一） |
| clickhouse | 8123 | 列式分析引擎（扩展预留） |
| superset | 8088 | BI 仪表板 |
| app | 8501 | Streamlit NL2SQL 问答 |

**配置与安全**：全部密钥经 `${VAR:-默认}` 从 .env 注入（.env 不入库，提供 .env.example 模板）；数据卷挂载 `./data:/data` 保障 HDFS warehouse 数据持久化；一键重建脚本 rebuild_pipeline.sh 实测 3 分 22 秒完成全链路恢复（数据自愈演练通过）。

## 八、关键工程实践

1. **回收站陷阱**：本镜像开启 Hadoop 回收站，普通 DROP 后同名重建会读到残留旧数据；所有同名重建一律 `DROP TABLE ... PURGE`；
2. **大额隔离**：≥10 万断档订单不做伪还原，STG3 留痕、DWD 过滤，分析层金额全部落在可信区间；
3. **编码映射维表**：dim_pay_type / dim_member_level 承载"原始编码 → 中文标准名"映射，LEFT JOIN 校验未映射行数必须为 0；
4. **存储选型**：ODS/STG 保留 TEXTFILE 便于贴源与排查，DWD/DWS/ADS 统一 ORC 列式，兼顾压缩比与扫描性能；
5. **Superset 自动化**：REST API 全自动配置数据集/6 图表/仪表板/筛选器（表单登录 → 会话 → JWT → X-CSRFToken 组合鉴权），环境重建后 5 分钟内仪表板自动就绪；
6. **前端离线化**：大屏将 echarts.min.js 与 GeoJSON 全部 vendor 化，单 HTML 离线可开，适配机房无外网场景。
