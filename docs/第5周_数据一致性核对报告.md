## 三、联调中发现的 Bug 与修复（本次核对的核心价值）

### Bug：重建脚本不可重复执行，ODS 数据翻倍

- **现象**：首次重建后核对发现 ods_order 31,200 行（预期 15,600）、ods_user 2,000（预期 1,000）——全部翻倍；
- **根因**：ODS 六表为**外部表**，`DROP DATABASE CASCADE` 不删除外部表数据文件；而 `LOAD DATA ... INTO TABLE` 是**追加语义**。容器重建后元数据还在（MySQL 卷保留）但 warehouse 数据丢失，重建时旧数据目录残留 + 再次 LOAD，每个 CSV 进表两份；
- **修复**：rebuild_pipeline.sh 增加前置 reset 步骤——先 DROP 四库元数据，再物理删除 warehouse 中 `ydsh_*.db` 残留目录，使脚本可任意重复执行；
- **修复后复测**：重建 3 分 25 秒 → 全部行数恢复预期 → 指标三方对照一致；
- **启示**：这正是部署手册「常见问题」类陷阱的典型形态——LOAD 追加语义在脚本注释中早有警告，但只有联调实测才暴露了它与外部表生命周期叠加后的组合风险。

### 顺带修复

- `app/Dockerfile`：`COPY requirements.txt` 修正为 `COPY app/requirements.txt`（build context 为项目根，原路径在全新机器上构建必失败）。
