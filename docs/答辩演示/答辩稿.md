## 一、项目概览（0:50–3:30）

### 第 3 页　章节扉页

先看第一部分，项目概览。

### 第 4 页　业务背景与需求分析

云购生活是一家**线上线下一体的新零售企业**，有门店、有电商、有会员体系。我们接手的时候，发现四个问题。‖

**第一，数据孤岛。** 订单、商品、门店、用户、行为，分散在六张表里。想看"某个门店某个品类卖得怎么样"，得手工 join 四张表。‖

**第二，质量失控。** 同一张订单表里，手机号有带横杠有不带；日期有 `2024/1/5`、也有 `2024-01-05`；性别字段能写出**八种**值。‖

**第三，口径不一。** 财务算的 GMV 和运营算的对不上——因为一个含退款、一个不含。‖

**第四，取数靠人工。** 业务想看个数，要提需求、排队、等开发写 SQL。‖

〔手指屏幕〕所以我们的目标**不是"做一个看板"**，而是**建一套让口径唯一、取数自助的数据底座**。这就是需求文档里 BR1 到 BR4 的由来。

### 第 5 页　全流程数据链路

这是全链路。‖

左边是**六张原始 CSV**，进 **ODS 贴源层**——一行都不改，只做留证；中间经过**五步清洗**进 **DWD**，按星型模型组织；再往上 **DWS** 做五个粒度的汇总；最上面 **ADS** 出六张应用表，**一张对应一个看板主题**。‖

右边是三端消费：**Superset 自助分析、大屏汇报、Streamlit 问答**。下面这条是支撑层：Python 做预测建模和 KPI 计算，再镜像一份到 MySQL 给报表层用。

### 第 6 页　系统总体架构

架构上我想强调一点：‖ **分层不是为了好看，是每一层对应一类问题。** ‖

ODS 解决"原始数据不能动"——出问题能回溯；DWD 解决"清洗规则要可审计"——每条规则都在 SQL 里；DWS 解决"不要每次重算"；ADS 解决"口径只定义一次"。‖

这条原则后面会反复出现：**所有指标只在 ADS 定义一次，三端都读同一张表**，所以三端的数字**必然一致**。‖ 〔停顿〕**这不是巧合，是设计。**

## 二、数据治理与建模（3:30–5:50）

### 第 8 页　数据清洗成果

五类脏数据，**全部处理完，修复率 100%**。挑三个说。‖

**重复记录**：600 行冗余，用 `ROW_NUMBER` 按主键去重，保留最新一条。‖

**日期格式不统一**：2,027 条，统一成 `yyyy-MM-dd`——因为后面分区要用它。‖

**最有意思的是金额异常**，我们拆成两种：**负金额 310 条**，判定是符号写错，取绝对值；**大额断档 304 条**，单笔超过十万的，我们**没有"猜"一个合理值**，而是隔离到 STG3 留痕、DWD 层过滤。‖

〔放慢〕因为**编一个数字出来，比缺一个数字更危险**。‖

所以行数对账是**闭环**的：ODS **15,600**，减 **600** 去重、减 **304** 大额，正好等于 DWD 的 **14,696**。‖ 这个等式写在清洗报告第三节，老师可以核。

### 第 9 页　星型模型与四层落地

建模这块：**五张维度表、四张事实表**，围绕订单这个核心。‖

DWS 五个粒度——**天×整体、天×品类、天×门店、天×渠道、用户全期**，全部从 DWD 聚合，**不跨层取数**。‖

ADS 六张表，一张对应一个看板主题：KPI 大盘、GMV 趋势、品类排行、门店排行、渠道分布、用户价值分层。‖

命名也统一了：`ods_` / `dwd_` / `dws_` / `ads_` 前缀——**看表名就知道它在哪一层**。

## 三、AI 分析与可视化 + 现场演示（5:50–8:50）

### 第 11 页　KPI 指标体系与 GMV 预测建模

**11 项 KPI 口径统一在一张表里**：GMV、订单数、客单价、复购率、退款率这些。‖

预测这块我们做了 **3 个模型加 2 个基线**：霍尔特线性趋势、霍尔特-温特斯、SARIMA，基线是移动平均和朴素法。测试集上**霍尔特线性趋势最好**，MAE 和 MAPE 都最低。图上蓝线是真实值，橙线是拟合，右边七天是预测。‖

〔停顿，看老师〕这里我想说一个判断：我们**没有**因为"深度学习更高级"就上 LSTM——**366 天的数据量，上复杂模型只会过拟合**。‖ **选模型看数据量，不看时髦。**

### 第 12 页　NL2SQL 智能问答

NL2SQL 解决的是"**业务人员不想学 SQL**"。左边这句话"整体经营大盘"，右边出来 SQL、表格、图。‖

关键在**它怎么选表**：它自己选中了 **ADS 层的 kpi 表**，而不是去扫 ODS 明细。这是 schema prompt 里给的**语义约束**——告诉模型每张表是干什么的。‖

我们做了**双引擎**：有大模型密钥走大模型，没有就降级规则引擎，**保证任何时候都能用**。‖ 这个我在现场演示一下。

〔切浏览器 → 演示① Streamlit，约 60 秒，步骤见第二部分〕

### 第 13 页　三端可视化

三端总结一下：**Superset 给分析师**，自由探索；**大屏给管理层**，一屏看清；**Streamlit 给业务**，用中文问。‖ **三种消费方式，一个数据底座。** ‖ 这也是我们跟"做三个看板"的本质区别。

### 第 15 页　工程化实践与项目复盘

工程化四件事。‖

## 老师高频追问的预备答案

| 问题 | 回答要点 |
| --- | --- |
| 为什么分四层，不分三层？ | ODS 贴源不改一行数据，保留追溯证据；DWD 才承载清洗规则。合并会导致"清洗不可回溯"，出问题查不到原始值 |
| 清洗后行数为什么少了 904？ | −600 是订单号重复去重，−304 是金额异常（超 10 万）剔除，对账公式写在清洗报告第 3 节 |
| 指标口径怎么保证一致？ | 所有指标只在 ADS 层定义一次，DWS 只做汇总不做口径；三端都读同一张 ads_kpi 表，所以三处数字必然一致（已实测核对） |
| 数据丢了怎么办？ | 已实战演练：`rebuild_pipeline.sh` 一键重建，3 分 22 秒恢复全链路，GMV 与重建前完全一致 |
| 遇到过什么真 Bug？ | 重建脚本不幂等——Hive 外部表 `drop cascade` 不删数据文件，`LOAD` 又是追加语义，导致 ODS 翻倍到 31,200 行。修复：重建前物理清理 warehouse 目录 + 脚本加幂等判断 |
| 团队协作怎么留痕？ | 2 个真实 PR 合并 + 双 feature 分支 + 40 余次约定式提交，`docs/Git提交历史.txt` 与审查报告可查 |
| 这个项目能上线吗？ | 能：`docker compose up -d` 六服务一键起，含 healthcheck 与依赖顺序；生产还需补：密钥外置（已用 .env）、Superset 元数据库换 PostgreSQL、加监控告警 |

## 回答提问的三步法

**第一步：复述问题**（确认理解，同时争取 3 秒）

"您问的是 XX 指标为什么这么定义，对吗？"

**第二步：给结论 + 依据**

"我们的口径是 XX，依据是 XX。这个定义写在需求文档第 X 节 / ADS 建表注释里。"

**第三步：承认边界**

"不过您提到的这个场景我们**没有覆盖**——比如退货后的二次下单，目前是算在新订单里的。这是一个已知的简化。"

第三步最重要。坦诚承认边界，比硬编一个理由更让老师认可。
